<p className="lead">I set out to move my blog from a hardcoded TypeScript array to MDX files. Before writing a line of the new pipeline I measured what the old one actually rendered, and found three bugs that had been live the whole time. None of them threw an error. That is exactly why they survived.</p>

## The posts were rendering with no typography at all

The article template had looked right to me for months:

```tsx
<div className="prose dark:prose-invert max-w-none">
  {/* post body */}
</div>
```

That is the standard incantation. The problem is that `prose` comes from `@tailwindcss/typography`, and the plugin was never installed. Tailwind v4 does not auto-load plugins, and there was no `@plugin` line in my CSS. So `prose` was a class name that matched nothing.

I only caught it because I stopped reading the markup and measured the rendered page instead:

```js
const h2 = document.querySelector(".prose h2")
getComputedStyle(h2).fontSize    // "16px"
getComputedStyle(h2).fontWeight  // "400"
```

A heading rendering at 16px and weight 400 is not a heading. It is a paragraph. Checking the rest confirmed how complete the failure was:

| Element | What it was | What it should have been |
| --- | --- | --- |
| `h2` | 16px, weight 400 | 24px, weight 700 |
| `p` | `margin-bottom: 0` | about 1em |
| `li` | `list-style-type: none` | disc |
| `pre` | no background | a contrasting block |

Every post was a single undifferentiated wall of 16px text. I had read those pages many times. Because I already knew the structure of my own writing, my eye supplied the hierarchy that the CSS was not providing.

The fix was one line in `globals.css`:

```css
@import "tailwindcss";
@plugin "@tailwindcss/typography";
```

**A class that does nothing looks identical to a class that works.** Nothing in the build, the linter or the type checker can tell you that a string in a `className` matched zero rules. Only the rendered page knows.

## One utility class was corrupting text on every page

My root layout had this on the `<body>`:

```tsx
<body className={`${geistSans.variable} antialiased capitalize`}>
```

`capitalize` sets `text-transform: capitalize`, which uppercases the first letter of every word. On the entire site. Forever.

Some of what it did was merely wrong:

- "Back to Blog" rendered as "Back To Blog"
- "7 min read" rendered as "7 Min Read"
- "Why I Switched to Tailwind CSS" rendered as "Why I Switched To Tailwind CSS"

And some of it was genuinely broken. My own email address rendered as `Mehediimun@gmail.com`. For a blog with slash commands in it, `/plugin install ecc@ecc` would have rendered as `/Plugin Install Ecc@Ecc` — not a typo, but corrupted content, in a code-adjacent context where case carries meaning.

What interests me is how it survived. It survived because I kept patching around it. There were **seventeen** `normal-case` classes scattered across the codebase — in the about page, the projects pages, the contact page — each one locally undoing the global rule. I had written every one of them myself, one at a time, each solving the immediate symptom.

**When you find yourself writing the same override repeatedly, the override is not the fix.** The default is wrong. Seventeen patches was the codebase telling me so, and I read it as seventeen unrelated small fixes.

Deleting `capitalize` fixed all of them at once. It also revealed that my headings were authored in sentence case and had been Title Cased against my intent for months.

## The font I picked was never actually used

This one is the most humbling. The layout loaded Geist properly:

```tsx
const geistSans = Geist({ variable: "--font-geist-sans", subsets: ["latin"] })
```

and applied the variable to the body. The CSS defined the theme token:

```css
@theme inline {
  --font-sans: var(--font-geist-sans);
}
```

Both halves were correct. Nothing connected them. Defining `--font-sans` makes the `font-sans` utility available; it does not apply anything on its own, and nothing in my markup ever used it. So the browser fell back to its default stack, and the whole site rendered in the system font.

```js
getComputedStyle(document.body).fontFamily
// "-apple-system, BlinkMacSystemFont, 'Segoe UI', Roboto, ..."
```

I develop on Windows, where that resolves to Segoe UI. Segoe UI and Geist are both neutral geometric sans faces. At body size, on my monitor, I could not tell them apart — so for months I looked at a font I had not chosen and thought it was the one I had.

The fix was adding `font-sans` to the body. One class, and the site finally rendered in its own typeface.

## What these have in common

None of them produced an error. The build passed, the types checked, the linter was clean, and every page returned 200. A test asserting "the heading renders" would have passed, because the heading did render — just at 16px.

They share a shape: **the code expressed an intention, and I verified the intention rather than the result.** I read `prose` and thought "typography". I read `Geist(...)` and thought "Geist". Both were reasonable readings of the source, and both were wrong about the page.

The habit I have taken from this is narrow but useful: for anything visual, read it back from the browser. Not a screenshot — the computed value.

```js
// Is my typography plugin actually loaded?
[...document.styleSheets]
  .flatMap((sheet) => [...sheet.cssRules])
  .filter((rule) => rule.selectorText?.includes("prose")).length
// I expected dozens. I got 0.
```

That number was the entire bug, available at any point in the previous months, from one line in a console I had open the whole time.

## Worth checking on your own site

Three probes, none of which takes longer than a minute:

1. **Does your typography plugin actually apply?** Count the rules matching `prose`, as above. Zero means the class is decorative.
2. **Is any `text-transform` inherited from a wrapper?** Run `getComputedStyle(document.body).textTransform`. Anything but `none` is reaching every string on the page, including addresses and code.
3. **Are you rendering the font you chose?** Log `getComputedStyle(document.body).fontFamily` and check the name you picked comes first — and that `document.fonts` actually loaded it.

The rest of the rebuild — MDX files, build-time syntax highlighting, per-post OpenGraph images — was the part I had planned. These three were the part I found by looking, and they turned out to be the more valuable half.
